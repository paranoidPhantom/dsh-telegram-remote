# Telegram Remote: supervised-process architecture

## Implementation status

The TypeScript implementation under `src/` splits the DSH Host plugin from a supervised Telegram child process. This is no longer only a process-isolation proposal. It is also not an independent daemon: **DSH must remain running**. The implementation and its recovery paths are evolving; source wiring and mock-based tests do not establish successful installed Desktop activation, lossless recovery, Telegram eligibility or visually verified behavior.

## Ownership and integration

- **Host — `src/index.ts`, `src/host/`, `src/bridge/`, `src/projection/`:** Cordis registrations, DSH session truth/projections, credential authority, settings route, model/prompt/steer/stop mutations, approval decisions, confined filesystem access, storage and resource handles.
- **Child — `src/child/`, `src/bot/`, `src/telegram/`, `src/delivery/`, `src/rendering/`, `src/widgets/`:** Telegram polling, callback routing, topic/model surface, drafts, rendering, outbound scheduling, native media and widget compilation/delivery. Host-created resource descriptors provide bounded file/widget bytes over RPC rather than arbitrary child filesystem authority.
- **Client — `src/client/`:** the Harness Settings UI, compiled to the root classic-script `client.js`; it is not a standalone application.

The Host adapts DSH projections to semantic run views containing normal outputs, tool summaries, bounded explicit model-reasoning previews, status and touched-file metadata. Reasoning previews contain only provider/session reasoning text (240 characters each, at most 64 per turn), never encrypted content, signatures, replay payloads or raw internal state. They are escaped and localized as reasoning in collapsed logs only, not answers or drafts. Chronological activity/logCount boundaries are separate from real toolLog/toolCount values. It does not serialize live Cordis/Agent/Session objects or raw reasoning chunks. The child asks the Host for explicit allowlisted capabilities through `src/child/host-port.ts` and `src/host/authority.ts`.

Credentials remain in DSH under `telegram-console/bot`. The child obtains the token over the private parent/child IPC channel; it must never appear in argv, inherited environment, logs or browser responses. Generation and owner-epoch fences constrain requests, while Host mutations additionally check actor/topic ownership. Approval IDs are Host-owned, expiring and cancellable; only authorized Telegram actions may settle them. A process boundary is not an OS sandbox or a guarantee that a compromised child is harmless.

## Process lifecycle and IPC

`src/host/launcher.ts` uses a non-detached fork with a sanitized environment, empty `execArgv`, ignored console streams and one private IPC channel. `src/host/supervisor.ts` checks a version/build/generation/PID handshake, applies startup/shutdown deadlines, supervises established-child exits with exponential backoff and a restart budget, and terminates only its owned process handle. There is no in-process fallback. The suite exercises the actual launcher and extracted archive child entry in this environment (Electron in explicit Node mode), including handshake and shutdown without Telegram initialization. Installed Desktop plugin activation remains a separate verification step.

`src/host/lease.ts` provides local filesystem exclusion keyed by Telegram bot identity. Initialization checks bot identity/webhook state and acquires the lease before polling. This is local exclusion, not a distributed lease across machines. POSIX directory/file ownership and mode checks apply on POSIX only; Windows synthetic mode/uid fields are not ACL checks. On Windows the lease relies on inherited permissions of the user's temporary directory, not a new explicit DACL audit. Directory/link rejection, pathname/descriptor identity checks, exclusive file creation, and owned-record/PID fencing remain enforced on all platforms. Rotation and unload close the owned child before releasing exclusion or closing Host stores. IPC disconnect triggers child shutdown; parent-side termination escalates if graceful shutdown does not exit. Verify those paths in the installed runtime before claiming uninstall/restart cannot leave a poller.

After acquiring the bot lease, the child starts polling and refreshes the owner's chat-scoped Telegram command menu as tracked background work; menu requests do not block initialization. It replaces the language-neutral and en/zh/ru lists using the DSH-selected locale, and refreshes them on locale changes. Locked/unconfigured owners do not register commands. Menu registration failures are reported but do not disable polling; the next startup or locale change retries synchronization. Other pre-existing Telegram language-specific scopes are not managed.

`src/protocol/` validates versioned JSON envelopes `{version,generation,id,type,payload}`, bounds serialization and RPC pending/queued capacity, supports cancellation/timeouts, and does not implicitly retry side effects. IPC acceptance, handler completion and Telegram acceptance are different events. Timeouts and lost IPC can leave a side effect uncertain even when the caller receives an error.

## Inbound admission and queue behavior

`src/host/inbox.ts` owns `console:inbox` and the compatible `poll-offset` key in the `telegram_console_delivery` / `delivery` store. Admission is serialized: it writes the update entry before advancing the polling offset. These are **two storage writes, not a transaction**. A retry can repair an offset write after the entry was stored. Entries have terminal completed/failed/uncertain outcomes; unresolved capacity and serialized bytes are bounded, and settled history is compacted. Finite retained identity history is not unlimited deduplication.

`src/child/ingress.ts` separates polling/admission from handler completion. Its dispatcher rereads unresolved Host entries rather than keeping an unbounded child backlog. Normal work is bounded and gated per topic; Stop and recognized approval callbacks have a reserved serial priority slot. Routing priority never grants authority. Native Stop draft IDs accept numbers or decimal strings and normalize before exact draft authorization. A classification-rejected entry is settled failed without executing it, using a bounded tracked slot, so malformed updates cannot poison the entire replay scan. Ingress diagnostics expose an aggregate error count without retaining update contents or backend error strings. Capacity rejection stops admission of the remainder of that batch. Settlement persistence failure halts ingress rather than blindly executing the same work again; abort marks an unfinished outcome uncertain when settlement is possible.

Important recovery limits:

- The entry-before-offset ordering relies on the actual storage adapter's write/durability guarantees; it is not proof of crash-safe disk commits.
- Update admission is not execution acknowledgement. A child crash after a DSH or Telegram side effect but before settlement can leave unresolved work. The operation journal protects selected Host mutations, not every Telegram side effect.
- Pending replay is filtered by the current owner epoch. Same-owner Host reload retains its persisted epoch so admitted work remains recoverable. An owner change increments the epoch and settles old unresolved entries as uncertain; it never grants their authority to the new owner. Bot identity changes reset the bot-specific inbox/offset and detach old topic bindings.
- A native topic-creation service event alone does not initiate model confirmation: Telegram can auto-create topics for commands such as `/sessions`. Commands are answered in that topic without binding or deleting it; a non-command prompt or explicit `/new` initiates session confirmation. Pending model-confirmation state, callback maps and drafts have child-memory state. Journaling the original update does not by itself restore that state.

## Host operations, receipts and output recovery

`src/host/operations.ts` journals operation identity and running/complete results. Completed results can be reused; in-progress non-idempotent operations are uncertain and suppress automatic replay. Prompt replay uses the original request ID and depends on DSH's idempotency contract. This journal cannot make a remote side effect exactly-once, and journal retention/cleanup must be evaluated separately.

`src/delivery/console-delivery.ts` records committed-output IDs, hashes, Telegram message IDs and completion. Before each normal output chunk it persists a pending marker; accepted message IDs are saved before cosmetic updates. An interrupted pending send is durably quarantined as `uncertain`, suppressing automatic resend without blocking later outputs in the same turn, later turns, or other topics. Definitive non-rate-limit Telegram 4xx send rejections are quarantined as `rejected`; formatting failures are `invalid`. Quarantined outputs retain IDs/hashes and accepted message IDs, never gain `complete`, and emit bounded content-free warnings. A processed run's `final` flag does not establish successful delivery of quarantined outputs. Even a stored message ID with a still-pending marker can require reconciliation. Telegram provides no general send idempotency key: do not equate a transport error with a definitive rejection or claim all artifact/topic/widget sends share the normal-output receipt guarantees.

The conversation checklist consumes only successful semantic `todo/write` events, not tool-call arguments. Projection v8 retains its latest checklist across turns; the child validates the snapshot and renders one bounded, escaped en/zh/ru checklist per topic. The first nonempty checklist is sent silently, its accepted message ID is stored in topic delivery metadata before pinning, and later changes edit that same message. Pin failures retry the pin without resending. It never owns final controls, unpins the initialization card, or stores checklist text in delivery metadata. Empty updates clear an existing checklist but do not create the first one. Topic context, tombstones, owner fencing and the existing serial/lifecycle cancellation apply. Explicit Telegram 4xx send rejection permits retry; an ambiguous transport/server failure or crash after the pending marker suppresses automatic resend and requires receipt reconciliation. Telegram has no general send idempotency key; this is not an exactly-once guarantee or proof of real Telegram pin appearance. Deleting an individual checklist message is not automatically repaired.

Host publication coalesces replaceable semantic progress snapshots. Durable boundaries are reconstructed from authoritative session observations, with `console:source:<session>` recording the last acknowledged source sequence for the owner epoch. The source cursor records processed delivery boundaries: it advances after an explicit child `delivered` acknowledgement or a `warning` acknowledgement backed by retained quarantine evidence, not merely after trying a send. A warning is not a successful delivery claim; detached topics do not advance it. Invalid historical receipts remain untouched and produce warnings; prior malformed rows do not block later valid turns. Isolated observation, event-fold or generic handler failures are warned and replay continues to later boundaries/topics, but an unacknowledged prefix keeps its cursor/watermark behind the failure. Storage, authority, transport and cancellation failures still fail closed. Catch-up snapshots are explicitly marked across IPC and deliver committed outputs/logs directly, without creating transient placeholders, drafts or heartbeat registrations. Live progress snapshots retain native draft behavior; Telegram outbound pacing still applies to history delivery. The catch-up lane retains one active scan and one dirty rerun instead of a promise per event. Large views transfer in bounded chunks with a 10 MiB aggregate limit; exceeding that limit fails explicitly rather than silently truncating committed text. This relies on the existing Host observation API returning the full ordered session history and on the backing store's durability; tests and code do not establish real Host disk-commit guarantees or exactly-once Telegram sends.

Isolation also does not eliminate head-of-line delays: Host IPC/storage/DSH calls can stall admission and mutations, session queues still mix work, and sealing a tool-log segment is awaited before its following answer. Telegram send/edit/draft pacing and global 429 cooldowns still apply. Coalesce replaceable progress, never intentionally discard committed answers or unresolved approval decisions. Runtime status includes bounded child identity, queue counts, current cooldown, 429 retry-duration samples and child-event-to-send-start latency samples. Those samples exclude Host-side source-event time and do not prove accepted delivery. Status/last-error fields and suppressed cosmetic errors are not a complete delivery trace.

## Native rich replies

Markdown assistant outputs and answer drafts use `sendRichMessage` / `sendRichMessageDraft` with sanitized Rich Markdown; fallback preview edits use `editMessageText.rich_message`. Plain status/tool surfaces retain the existing entity/HTML carrier. Headings, lists/tasks, tables, quotes, inline styles, code, footnotes and formulas are passed to the native rich parser rather than flattened. Raw HTML is escaped outside code; image/media syntax is reduced to safe external links or local code labels, with no model-created interactive controls or automatic media fetching. Pathological oversized/deep formatting is shown as literal code. Rich chunks use a conservative 16,000-source-byte/250-block-unit budget; huge code blocks are reopened per chunk. Large tables/paragraphs may span messages. Existing legacy receipts retain their original representation/chunk boundaries; new rich output receipts and legacy-final receipts record `rich-v1` before sending. Ambiguous sends are not retried as legacy text. Shared pacing, Stop IDs and output deduplication remain unchanged. Unit/transport mocks verify payloads and safety, not production Telegram eligibility or actual visual rendering.

## User-question forwarding

Blocking generic `user-questions/request` events for mapped sessions are forwarded to Telegram as bounded question DTOs (up to 12 questions, 30 options each, 128 KiB total). The contract follows upstream Harness documentation; installed Desktop live inspection was unavailable and this compatibility is not activation evidence. Missing topics, timed waits, specialized approval/plan intents and unsupported shapes delegate to the existing answerer chain. Timed waits/continued late replies are not implemented here.

The Host owns random single-use question capabilities and validates the complete answer batch against exact original question IDs/option labels. Submission requires the current generation, owner epoch, owner-only private chat, exact topic and live untombstoned mapping. The child presents sequential single/multiple choices, explicit custom replies and skipped items; it never answers on behalf of the user or converts answers into normal prompts. Question keyboards are protected from general toolbar cleanup. Abort, authority rotation and shutdown revoke pending capabilities; state is memory-only and no automatic question recovery is promised. A presentation RPC result is not answer authority. Child submission is awaited inside the authenticated callback/reply actor scope. Long supporting text is escaped/chunked without dropping detail; Telegram delivery/cleanup failures can leave stale inert cards. Batch intermediate selections are not Host answers until final submission. The existing Telegram lanes and backpressure remain in effect.

## Startup debug log

The active installed package writes `.runtime-status.json` (or the configured `statusPath`). Plugin Manager generations can move the package directory; do not look in a source checkout or assume a historical generation. Settings → Telegram Remote → **Copy debug log** retrieves the current bounded snapshot through the same owner-authenticated, no-store settings route, without reading credentials or arbitrary file contents.

The JSON is limited to **100,000 UTF-8 bytes**, atomically replaced by one coalescing writer, with at most 256 startup events. Oldest events are evicted first and `startupLogDropped` counts omissions. History covers the current Host activation only; it is not an append-only archive across Host restarts. Each event has a Host timestamp, sequence, launch-attempt number, source, fixed stage/outcome, and optional duration or allowlisted numeric/code metadata. Startup coverage includes configuration and credential presence/read, child launch/handshake/exit/restart, initialization, `getMe`, webhook checks, lease acquisition, each language-specific command registration, ingress start and Host replay. Command-registration failure remains nonfatal and is recorded independently of polling. Initialization has a 180-second RPC budget, distinct from the 5-second process handshake. An initialized worker's delivery acknowledgements have a 300-second budget. Initialization failure requests generation-fenced recovery using the existing supervisor restart budget, retaining the Host bot lease until owned-process exit; isolated replay failures leave the initialized worker online and do not blindly restart/resend uncertain deliveries. Explicit quarantined-output warning acknowledgements advance the processed cursor; failures without such acknowledgement leave the affected prefix unadvanced while later topics/boundaries are still attempted.

Replay diagnostics identify topic enumeration, topic lookup, cursor reads/writes, session observation, delivery, and observation disposal using topic ordinals and source sequence numbers—not session IDs or message content. Delivery failures identify `run.push` versus chunk-transfer/commit RPCs. Both RPC endpoints observe handler exceptions before generic `HANDLER_ERROR` replacement and record allowlisted method, error type, numeric Telegram status and safe cause code; observer failures/timeouts never change the generic wire error. Look immediately before a failed replay event for the corresponding `runtime-error` / `rpc-handler` event from the child or Host. Unrecognized causes still remain `UNKNOWN`, not raw messages.

No tokens, request URLs, webhook URLs, raw exception strings/stacks, Telegram response bodies, command text or environment dumps are retained. Errors use a fixed code vocabulary and numeric Telegram status; unrecognized errors are `UNKNOWN`. Pre-handshake crashes can only expose process/handshake observations, not the discarded child stderr. Status-file write failures cannot be recorded into that same unwritable file; the Copy action can still export the bounded in-memory snapshot when the settings route is active. These diagnostics do not establish successful Telegram delivery or complete visibility into startup before plugin code executes.

## Verification and remaining obligations

Run `npm run typecheck`, `npm run typecheck:test`, `npm test`, `npm run test:isolation` and `npm run build`. Isolation tests live under `test/isolation/` and cover protocol/RPC, supervision, lease, ingress/inbox, authority, approvals, operation identity and resources. Inspect the emitted archive, including the actual child entry and generated Client, as described in [AGENTS.md](AGENTS.md). Passing unit tests alone does not establish:

1. Real Node and Desktop/Electron child launch/handshake and correct installed package layout.
2. Child crash, lost IPC, parent death, unload/reload, restart-budget exhaustion and uninstall without a second/orphan poller.
3. Actual store write ordering/durability, duplicate admission, capacity pressure, operation uncertainty and recovery after accepted-but-unrecorded Telegram sends.
4. Durable session-output gap recovery across busy Host, multiple turns/topics, cache eviction and long histories; do not call the cursor work complete prematurely.
5. Credential/admin rotation fencing, old-owner topic/control revocation, approval cancellation, locale propagation and pending native-topic prompt handling across restart.
6. Real Telegram/Desktop appearance or availability of typing, drafts, Stop, custom emoji, rich text, native media or widgets. Preserve widget source-document fallback; process isolation makes no server-eligibility promise.

Record implementation, unit-test, activation and visual evidence separately. Keep existing credential/storage/section identifiers stable; process isolation is not a reason to rename persistent keys or create a competing DSH session database.
